# pa_booking_service — контекст для Claude Code

Микросервис **записей и бронирований** для Личного Кабинета Оператора. Два
независимых модуля:

- **Записи** — к психологу и на консультацию МКР (матрица карьерного роста).
  Один специалист, один календарь слотов, тип записи — `psy | mkr`.
- **Библиотека** — каталог книг, бронь на 7 дней, продление, возврат.

Переносит функционал eXpress-ботов `psy_bot_v2` и `Library_bot` в ЛК; боты после
переезда отключаются. Identity — из `pa_auth_service`, наружу отдаётся через
`pa_bff` (mesh: `X-API-Key` + `X-User-Id` / `X-User-Roles`).

> **Дизайн и принятые решения — в
> `docs/superpowers/specs/2026-10-02-booking-service-design.md`** (источники
> переноса, модель данных, правила, API, перенос данных, выкатка). Этот файл его
> **не дублирует** — здесь только правила нашей совместной работы и общие
> конвенции. Спорные места сверяй со спекой.

## Кто я и как мы работаем

Я (пользователь) — разработчик, веду проект самостоятельно при помощи AI. Сервис
внутренний (только корпоративная сеть). **Принцип: код пишешь ты, но обязательно
показываешь и объясняешь, что и почему сделал.** Я остаюсь в курсе каждой строчки
и единственный, кто коммитит.

- Ты **можешь сам править файлы** через `Write`/`Edit`. Перед изменениями или сразу
  после — **показываешь правки и объясняешь** что/почему, с теорией там, где нужно.
- **Объясняй каждую новую концепцию до кода** (со ссылками на доку, если не базовое).
  На тестах построчно объяснять не нужно — важно достаточное покрытие.
- При сложных вопросах **проверяй гипотезы экспериментами, не предполагай.** На стыке
  знаний (контракт соседнего сервиса, поведение BotX/pybotx, формат старых таблиц
  MySQL ботов, on-premise URL) — **лучше спросить, чем угадать.** Сверяйся с
  реальной выдачей, а не с догадкой.
- **Бизнес-правила — как в проде ботов**, с расхождениями, явно согласованными в
  спеке. Не «улучшай» правило молча: если правило бота выглядит как баг — спроси.

## Git — коммичу и пушу только я

- Ты **не запускаешь** `git add` / `git commit` / `git push`. Никогда, даже «чтобы
  не потерялось».
- В конце батча работы **предлагаешь коммит-сообщение** по фактическим изменениям;
  решаю и коммичу я.
- **Сообщения — на английском, короткие.** Одна строка вида
  `prefix(scope): imperative summary`, до ~72 символов, без точки в конце.
  Тело — если без него непонятно «почему» или в батче несколько изменений.
  Код, докстринги и документация — на русском.
- Префиксы: `feat(...)`, `fix(...)`, `test(...)`, `docs(...)`, `refactor(...)`,
  `chore(...)`, `ci(...)`.
- Один коммит на батч работы (коммичу через `git add .`). Если в батче несколько
  изменений — перечисли их в теле коммита списком, а не дели на коммиты по файлам.

```
feat(appointments): enforce monthly booking limit
fix(library): allow returning overdue loans
test(domain): cover 14:00 MSK slot lock boundary
```

## Тесты и проверки

- Ступени разработки покрываем тестами — этап не считается закрытым без них.
- `ruff` и `mypy --strict` **прогоняешь сам** — это дёшево и быстро. После любых
  правок твоя ответственность — убедиться, что они чистые.
- **Простые тесты прогоняешь сам:** быстрые юнит-тесты по конкретному файлу/классу
  (`pytest tests/unit/test_x.py -q`), которые отрабатывают за секунды и дают
  короткий вывод. Это твой рабочий цикл — не спрашивай разрешения.
- **Тяжёлые тесты запускаю я:** полный прогон `pytest`, интеграционные (`db` /
  testcontainers), `external`, всё долгое или с многоэкранными трейсбэками —
  экономим токены. Ты пишешь **точную команду**, я возвращаю вывод.
- **Не подгоняй тесты под результат.** Если тест падает правдоподобной цифрой —
  это чаще баг в коде, чем в ожиданиях. Не меняй ассерт «чтобы прошло», не
  маскируй фейл через `pytest.skip`/`xfail` и не ослабляй проверку до
  «не упало». Сначала: сравни вход (наш запрос vs контракт), запусти диагностику,
  и **спроси меня**, если результат выглядит подозрительно («лимит не сработал на
  пятой записи», «чистка в 14:00 удалила занятый слот» — это сигнал, не норма).
- Числовые/структурные ассерты на реальные данные (перенос из MySQL ботов) пиши
  **из посчитанного значения** (разовый `SELECT COUNT(*)`), а не на глаз.
- **Не заявляй «работает/прошло», не запустив проверку.** Если прогон за мной —
  так и скажи: «жду вывод», а не «должно проходить».
- Маркеры: `external` — тесты в реальные системы (BotX), `db` — integration с
  testcontainers Postgres. По умолчанию пропускаются.

## Архитектурные рамки (главное)

- **Мы владеем доменом** записей и библиотеки: лимиты, окно 14:00 МСК, сроки
  броней — здесь. BFF только проксирует.
- **Мы не видим пользовательский JWT.** Его валидирует BFF по JWKS на краю;
  вниз идёт `X-API-Key` + проброс `X-User-Id`/`X-User-Roles`.
- **Host-порта нет.** Слушаем только `pa_net` (алиас `booking-api`).
- **Модули не импортируют друг друга.** `appointments` и `library` делят только
  инфраструктуру (БД, auth, notifier, xlsx, ростер) — чтобы библиотеку можно было
  вынести отдельно без переписывания.
- **Записи к психологу — чувствительные данные.** Видит их только роль
  `psychologist` (и сам записавшийся). `admin` другие роли неявно **не** покрывает.
- **Уведомления не откатывают операцию.** Отправка в BotX — после коммита; ошибка
  логируется и считается метрикой, бронь остаётся.

## Стек и конвенции кода

Зеркалим соседей (`pa_overtimes_and_charges` — ближайший образец, `pa_auth_service`,
`pa_bff`): Python 3.12+, FastAPI + Pydantic v2, PostgreSQL + SQLAlchemy 2.0 (sync) +
Alembic, Celery + RedBeat для периодики, structlog, prometheus-client, ручки
`/health` `/ready` `/metrics`. Dev: pytest, ruff, mypy --strict. Зависимости — в
`pyproject.toml` с верхними границами. Префикс настроек — `PA_BOOKING_`.

- **Pure `domain/`** — без знания про БД/HTTP/FastAPI. Вход/выход — dataclass'ы.
  Текущее время (`now`) передаётся параметром — правила тестируются без часов.
- **Время — Europe/Moscow.** «Сегодня», 14:00, границы месяца — по МСК, не по UTC
  контейнера. Даты — типы `date`/`time`, не строки (наследие ботов не переносим).
- **DI через `Protocol`** для внешних клиентов (BotX, ростер auth) — прод-обёртка +
  `Fake*` в тестах. Из обычных тестов в реальные сервисы не ходим.
- **Ключ пользователя — `employee_id` директории** (UUID из `X-User-Id`), не ФИО и
  не eXpress HUID. ФИО берём из локальной копии ростера.
- **Целостность — в БД.** От гонок защищают частичные уникальные индексы, а не
  «проверили, потом записали».
- Ошибки API: `{"detail": "<по-русски>", "code": "<машинный>"}`; чужой ресурс —
  404, а не 403 (не раскрываем существование).
- `@dataclass(frozen=True)` для value-объектов, `SecretStr` для секретов,
  keyword-only (`*`) после первого позиционного, когда параметров много.

## Локальный запуск

```bash
python -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"

ruff check .            # линт
mypy src                # типы (--strict)
python -m pytest        # тесты

uvicorn pa_booking.app:app --reload
```
