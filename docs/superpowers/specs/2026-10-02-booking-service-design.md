## 1. Цель и рамки

Записи к психологу и на консультацию МКР (матрица карьерного роста) и библиотеку
(бронирование книг) ведём в одном сервисе с одной БД. Пользоваться ими можно через
**два канала**:

- **ЛК** — только для сотрудников КЦ, только пользовательские функции;
- **eXpress-боты** `psy_bot_v2` и `Library_bot` — для всех, включая сотрудников не
  из КЦ, плюс админка специалиста и библиотекаря.

Ботами пользуются не только сотрудники КЦ, а ЛК сделан только для них, поэтому боты
не отключаются. Они становятся тонкими клиентами API сервиса: правила и данные
живут в одном месте.

**Критерий успеха:** сотрудник КЦ записывается и бронирует книгу в ЛК, любой
сотрудник — в боте, и оба канала видят одни и те же слоты, книги, брони и лимиты.
Специалист и библиотекарь работают в ботах. MySQL ботов больше не используется.

**Исходные решения (согласованы):**

| # | Решение |
|---|---|
| Р-1 | Психолог и МКР — **один специалист, один календарь**; различается только тип записи |
| Р-2 | ~~Пользователи полностью уходят в ЛК~~ (2026-10-07) → **два канала, ЛК и боты**, работают постоянно и параллельно над одной БД сервиса |
| Р-3 | ~~Связки HUID ↔ пользователь ЛК нет~~ (2026-10-07) → связка есть: учётка `express` в `pa_auth_service`, она приходит в ростере |
| Р-4 | Бизнес-правила — **как в проде ботов**, с явными расхождениями из §4.3. Расхождения действуют в обоих каналах |
| Р-5 | Уведомления специалистам — **в служебные чаты eXpress через BotX** (отправляет сервис). Об отмене специалистом пользователь узнаёт из личного сообщения бота (§6а) и из статуса записи в ЛК |
| Р-6 | Один сервис `pa_booking_service` с двумя изолированными модулями (не два сервиса, не домен в BFF) |
| Р-7 | Записи не стираются при удалении слота специалистом — получают статус `cancelled_by_specialist` |
| Р-8 | **Пользователя идентифицирует HUID eXpress** — в обоих каналах. В ЛК HUID берётся из ростера по `employee_id`. Нет привязки — запись и бронь в ЛК запрещены (Д-10) |
| Р-9 | **Боты — клиенты API сервиса**, в БД не ходят. Правила (лимит, 14:00, сроки) — только в `domain/` сервиса |
| Р-10 | **Админка — только в ботах.** Роль определяет сервис по HUID из своего env (`*_ADMIN_HUIDS`). Ролей `psychologist`/`librarian` в `pa_auth_service` нет |
| Р-11 | ЛК видит только пользовательские ручки; админские сервис принимает только из канала бота |

**Вне рамок:** перенос истории прошлых записей/выдач; уведомления пользователям по
email; лимит на число книг; ограничение числа продлений; админка в ЛК.

## 3. Архитектура

```
SPA ──Bearer──> pa_bff ──X-API-Key(bff) + X-User-Id──────┐
                 /api/appointments/* → /appointments/*    │
                 /api/library/*      → /library/*         ▼
                                                 pa_booking_service ──> PostgreSQL
eXpress ─webhook─> psy_bot_v2  ──X-API-Key(appointments-bot) + X-User-Huid──┤
eXpress ─webhook─> Library_bot ──X-API-Key(library-bot)      + X-User-Huid──┘
                                                   ├─ Celery beat: 14:00 МСК чистка
                                                   ├─ ростер из pa_auth (ФИО, HUID)
                                                   └─ BotX → служебные чаты eXpress
```

### 3.1. Каналы и идентификация (2026-10-07)

Канал определяется по `X-API-Key`. У каждого клиента свой ключ:

| Канал | Ключ | Кто пользователь | Доступные ручки |
|---|---|---|---|
| ЛК (BFF) | `PA_BOOKING_API_KEY` | `X-User-Id` → HUID из `directory_employees.express_huid`. Нет HUID → 409 `express_not_linked` | Пользовательские, обоих модулей |
| Бот записей | `PA_BOOKING_APPOINTMENTS_BOT_API_KEY` | `X-User-Huid` | `/appointments/*`, вкл. админские |
| Бот библиотеки | `PA_BOOKING_LIBRARY_BOT_API_KEY` | `X-User-Huid` | `/library/*`, вкл. админские |

- Ключ бота принимается только в ручках его модуля (чужой модуль → 401). Так
  модули остаются изолированными, и утечка одного ключа не открывает второй модуль.
- `X-User-Huid` из канала ЛК игнорируется, `X-User-Id` из канала бота тоже —
  выдать себя за чужой HUID через BFF нельзя.
- **Роль** вычисляет сервис: HUID ∈ `PA_BOOKING_APPOINTMENTS_ADMIN_HUIDS` →
  `psychologist`, HUID ∈ `PA_BOOKING_LIBRARY_ADMIN_HUIDS` → `librarian`. Админская
  ручка из канала ЛК → 403, даже если HUID в списке (Р-11). `X-User-Roles` сервис
  больше не читает.
- **ФИО** для уведомлений и выгрузок ищется по порядку: ростер по HUID (свежее) →
  снимок `user_name` в брони/выдаче → сам HUID. Бот передаёт имя из eXpress в
  `X-User-Name`. Заголовки HTTP не несут кириллицу, поэтому значение
  percent-encoded UTF-8 (`urllib.parse.quote`). Из ЛК снимок — ФИО из ростера.

Раскладка пакета `src/pa_booking/` по образцу `pa_overtimes`:

| Модуль | Назначение |
|---|---|
| `domain/appointments.py` | Чистые правила записей. Вход/выход — dataclass'ы, `now` параметром |
| `domain/library.py` | Чистые правила библиотеки |
| `domain/roles.py` | `Role(StrEnum)`: `psychologist`, `librarian`; роль — по HUID из `*_ADMIN_HUIDS` (§3.1) |
| `db/` | Модели SQLAlchemy, Alembic |
| `api/appointments.py`, `api/library.py` | Роутеры; друг друга не импортируют |
| `core/` | Настройки (`PA_BOOKING_`), M2M-auth, логи, метрики |
| `directory/` | Синк ростера `GET /v1/directory/roster` → локальная таблица ФИО (копия механики `pa_overtimes/directory`) |
| `notify/botx.py` | `Protocol Notifier` + BotX-реализация + `FakeNotifier`. Отправка без ожидания колбэка |
| `export/xlsx.py` | Выгрузки (`openpyxl`), общие для обоих модулей |
| `workers/` | Celery + RedBeat: чистка 14:00 МСК, синк ростера |

**Сеть:** без host-порта, только `pa_net`, алиас `booking-api`.

**BotX.** Используем существующие аккаунты ботов: аккаунт `psy_bot_v2` шлёт в чат
специалиста, аккаунт `Library_bot` — в чат библиотеки. Вебхуки остаются за
ботами (они живые, §6а); сервис через аккаунты только отправляет в служебные
чаты. Настройки на модуль:
`PA_BOOKING_APPOINTMENTS_BOT_ID`, `..._BOT_SECRET`, `..._NOTIFY_CHAT_ID` и
аналогичные `PA_BOOKING_LIBRARY_*`, плюс общий `PA_BOOKING_BOTX_CTS_URL`.

Отправка (решение 2026-10-03) — без pybotx: синхронный `POST
/api/v4/botx/notifications/direct/sync` с JWT бота, как в сервисе `express_notif`.
JWT (HS256, формат как `pybotx.auth.build_botx_jwt_v2`) подписываем через **`pyjwt`**.
Проверено 2026-10-06: сообщения от обоих ботов доходят в служебные чаты
(`tests/external/test_botx.py`). Прежние `HTTP 204` без доставки — следствие битой
строки в `.env` (непарная кавычка), а не поведение BotX.

## 4. Модель данных и правила

Все «сегодня», 14:00 и границы месяца — по `Europe/Moscow`.

### 4.1. Записи

```
appointment_slots
  id            bigint PK
  slot_date     date        NOT NULL
  slot_time     time        NOT NULL
  created_at    timestamptz NOT NULL
  removed_at    timestamptz NULL
  UNIQUE (slot_date, slot_time) WHERE removed_at IS NULL

appointment_bookings
  id            bigint PK
  slot_id       bigint FK → appointment_slots NOT NULL
  user_huid     uuid        NOT NULL          -- было employee_id (Р-8)
  user_name     varchar(256) NULL             -- снимок ФИО на момент брони (§3.1)
  channel       enum(lk, express) NOT NULL    -- откуда пришла бронь; для статистики
  kind          enum(psy, mkr) NOT NULL
  status        enum(active, cancelled_by_user, cancelled_by_specialist) NOT NULL
  created_at    timestamptz NOT NULL
  cancelled_at  timestamptz NULL
  UNIQUE (slot_id) WHERE status = 'active'
```

Слот удаляется мягко (`removed_at`) — история остаётся для выгрузок. Уникальность
активной брони на слот — защита от гонки: второй одновременный INSERT → 409.

| Действие | Правило |
|---|---|
| Свободный слот | `removed_at IS NULL`, нет активной брони, начало слота > `now` |
| Записаться | Слот свободен; у пользователя (по `user_huid`, все каналы вместе) **< 4 активных** броней со `slot_date` в месяце даты выбранного слота (прошедшие активные считаются, отменённые — нет). Advisory-блокировка — по HUID |
| Отмена пользователем | Только своей активной брони и только пока начало слота > `now`. Если `slot_date` = сегодня и `now` ≥ 14:00 — бронь `cancelled_by_user` **и** слот `removed_at = now`; иначе бронь `cancelled_by_user`, слот снова свободен |
| Чистка 14:00 МСК (beat) | Свободные слоты на сегодня → `removed_at`; если удалено ≥ 1 — уведомление в чат. При старте воркера после 14:00 — однократный догоняющий прогон (как в боте) |
| Специалист добавляет слоты | Пачкой `{date, times[]}`; дата не раньше сегодня (Д-8); дубли пропускаются → ответ `{added, duplicates}`. Слот на сегодня после 14:00 **разрешён** (как в боте) |
| Специалист удаляет слот | Свободный → `removed_at`. Занятый и ещё не начавшийся → `removed_at` + бронь `cancelled_by_specialist` + уведомление в чат; в ответе — отменённая бронь (`user_huid`, дата, время, тип), чтобы бот написал пользователю лично (§6а). Занятый и уже начавшийся → 409 `slot_in_past` (Д-9) |
| Мои записи | Брони с началом слота ≥ `now` в статусах `active` и `cancelled_by_specialist` |
| Обзор специалиста | Слоты месяца ±3 дня соседних (как в боте) с бронями, ФИО и типом |
| Выгрузки xlsx | За месяц и за всё время: дата, время, ФИО, тип, статус |

### 4.2. Библиотека

```
library_books
  id            bigint PK
  genre         varchar(255) NOT NULL
  author        varchar(255) NOT NULL
  title         varchar(255) NOT NULL
  description   text         NOT NULL
  created_at    timestamptz  NOT NULL
  removed_at    timestamptz  NULL

library_loans
  id            bigint PK
  book_id       bigint FK → library_books NOT NULL
  user_huid     uuid   NOT NULL               -- было employee_id (Р-8)
  user_name     varchar(256) NULL
  channel       enum(lk, express) NOT NULL
  starts_on     date   NOT NULL
  due_on        date   NOT NULL
  returned_at   timestamptz NULL
  returned_by_librarian boolean NOT NULL DEFAULT false
  created_at    timestamptz NOT NULL
  UNIQUE (book_id) WHERE returned_at IS NULL
```

Выдачи — одновременно история (замена `all_reserv_book`).

| Действие | Правило |
|---|---|
| Каталог | Книги с `removed_at IS NULL`; признак «свободна» = нет невозвращённой выдачи |
| Забронировать | Книга свободна → `starts_on` = сегодня, `due_on` = сегодня + 7. Лимита нет |
| Продлить | Своя невозвращённая выдача, `due_on` ≥ сегодня → `due_on += 7`. Число продлений не ограничено |
| Вернуть (пользователь) | Своя невозвращённая выдача, в т.ч. просроченная |
| Вернуть (библиотекарь) | Любая невозвращённая выдача; `returned_by_librarian = true` |
| Каталог (библиотекарь) | Добавить, изменить — всегда; удалить (мягко) — только если книга не на руках |
| Мои выдачи | Невозвращённые, просроченные помечены |
| Выдачи (библиотекарь) | `active` (`due_on` ≥ сегодня) и `overdue` (`due_on` < сегодня) |
| Уведомления в чат | Бронь, продление, возврат (с пометкой, если отметил библиотекарь) |
| Выгрузка xlsx | История выдач: книга, ФИО, начало, срок, дата возврата, кто отметил |

### 4.3. Согласованные расхождения с ботами

| # | Было в боте | Стало |
|---|---|---|
| Д-1 | Тип записи — свободный текст-ответ на «психолог или МКР?» | `kind: psy \| mkr`, свободного комментария нет |
| Д-2 | Можно отменить запись на сегодня и после её времени | Отмена только до начала слота |
| Д-3 | Просроченная книга пропадала из «Моих броней» (`end >= CURDATE()`), вернуть было нельзя | Просроченные видны и возвращаются |
| Д-4 | Возврат только пользователем | Библиотекарь тоже может отметить возврат |
| Д-5 | Админы — `ADMIN_HUIDS` в env бота | ~~Роли в `pa_auth_service`~~ (2026-10-07) → `*_ADMIN_HUIDS` в env **сервиса**, роль вычисляет сервис (§3.1) |
| Д-6 | Админ удаляет занятый слот → личное сообщение пользователю в eXpress | Статус `cancelled_by_specialist` (видно в ЛК и боте) **и**, как в боте, личное сообщение — шлёт бот по ответу сервиса (2026-10-07) |
| Д-7 | `ORDER_BOOK_LINK` в env бота | Ссылка «заказать книгу» — в конфиге SPA, сервис её не хранит |
| Д-8 | Выбор даты для добавления слотов включал 3 дня прошлого месяца — можно было создать слот в прошлом | Дата добавляемых слотов — не раньше сегодня (422) |
| Д-9 | Админ мог удалить любой слот в диапазоне, в т.ч. прошедший занятый | Прошедший занятый слот не удаляется (409 `slot_in_past`) — иначе состоявшаяся встреча пропала бы из выгрузки как «отменена специалистом» |
| Д-10 | — (ЛК не было) | Сотрудник КЦ без привязанной учётки eXpress в ЛК видит слоты и каталог, но записаться/забронировать не может: 409 `express_not_linked` (иначе один человек был бы двумя пользователями и обходил лимит). В боте он идентифицируется по HUID как обычно (2026-10-07) |

Д-1…Д-10 действуют в обоих каналах: бот ведёт себя так же, как ЛК. Видимые
пользователю бота изменения: тип записи — кнопкой (Д-1), отмена только до начала
(Д-2), просроченные книги видны и возвращаются (Д-3).

бота своего модуля и HUID из `*_ADMIN_HUIDS` (Р-10, Р-11).

### 5.3. Поток запроса (пример: запись)

1. BFF валидирует JWT по JWKS и зовёт сервис со своим M2M-ключом и `X-User-Id`
   (или бот зовёт со своим ключом, `X-User-Huid` и `X-User-Name`).
2. Зависимость auth определяет канал по ключу и выясняет HUID: из ЛК — по ростеру
   (нет → 409 `express_not_linked`), из бота — из заголовка. Роутер читает слот и
   число активных броней HUID в месяце.
3. Доменная функция проверяет правила (§4.1) и возвращает решение или ошибку.
4. Одна транзакция: INSERT брони, COMMIT (уникальный индекс ловит гонку → 409).
5. **После коммита** — `notifier.send(...)` с ФИО из ростера.

### 5.4. Ошибки

Тело: `{"detail": "<по-русски>", "code": "<машинный>"}`.

| Код | Когда |
|---|---|
| 401 | Нет/неверный `X-API-Key`; ключ бота в ручке чужого модуля; нет `X-User-Id` (ЛК) / невалидный `X-User-Huid` (бот) |
| 403 | Нет нужной роли; админская ручка из канала ЛК |
| 404 | Не найдено **или чужое** (существование чужого не раскрываем) |
| 409 | `slot_unavailable`, `monthly_limit`, `too_late_to_cancel`, `slot_in_past`, `book_unavailable`, `loan_overdue`, `book_on_loan`, `express_not_linked` (Д-10) |
| 422 | Невалидный ввод (Pydantic) |

**Сбой BotX** не откатывает операцию: warning в лог + счётчик
`booking_notify_failures_total{module}`. **ФИО не найдено** ни в ростере, ни в
снимке — в уведомлении/выгрузке HUID (§3.1). **Ростер не синхронизирован** — ЛК
не может найти HUID: `/ready` уже не готов (как раньше), запись из ЛК → 409
`express_not_linked`, бот работает.

### 5.5. Тексты уведомлений

Берутся из ботов с заменой username на ФИО:

- запись: `✅ {ФИО}\nЗаписался на {dd.mm.yyyy} в {hh:mm}\n{Психолог|Консультация МКР}`;
- отмена пользователем: `❌ {ФИО}\nОтменил запись на … в …\n{тип}`;
- удаление занятого слота: `Слот {дата} — {время} был удалён, запись {ФИО} отменена`;
- чистка: `Свободные окна на сегодня {hh:mm, …} были удалены`;
- библиотека: `{ФИО} забронировал книгу {title} ⏳\nДата возврата: …`, аналогично
  продление и возврат.

## 6. BFF и SPA

**pa_bff:** клиент `clients/booking.py` (`Protocol` + httpx + `Fake*`) по образцу
`clients/overtimes.py`; роутеры `api/appointments.py`, `api/library.py` —
проксирование 1-в-1 **только пользовательских ручек** (Р-11). Домена в BFF нет.

**SPA:** страницы `/appointments/*` и `/library/*` (конвенция неймспейсов).
Пункты меню — всем; админских вкладок нет (2026-10-07). Ошибки — по `code`, текст —
из `detail`; на `express_not_linked` — пояснение, куда обратиться за привязкой.
Ссылка «заказать книгу» — из конфига SPA.

## 6а. Боты (2026-10-07)

Боты `psy_bot_v2` и `Library_bot` остаются: интерфейс, кнопки, состояния диалога,
вебхуки BotX. Меняется только то, где данные и правила.

| Что | Было | Стало |
|---|---|---|
| Данные | `database.py`, свой MySQL | HTTP-клиент к `http://booking-api:8000` (§5); контейнер бота подключается к `pa_net` |
| Пользователь | HUID из входящего сообщения | Тот же HUID в `X-User-Huid` + имя в `X-User-Name` (§3.1) |
| Админы | `ADMIN_HUIDS` в env бота | Сервис отвечает 403 не-админам. Чтобы показывать или прятать админское меню, бот спрашивает `GET /{module}/me` → `{roles: [...]}` |
| Уведомления в служебный чат | Бот | Сервис (после коммита). Бот их не дублирует |
| Личное сообщение об отмене специалистом | Бот | Бот, по `cancelled_booking` из ответа `DELETE` (Д-6) |
| Чистка 14:00 | `slot_cleanup.py` в боте | Только Celery beat сервиса; из бота удаляется |
| Схема | `create_table` + `ALTER` при старте | Удаляется |
| Тип записи | Свободный текст | Кнопки «Психолог» / «Консультация МКР» (Д-1) |
| Возврат книги библиотекарем | Не было | В админке `Library_bot`: выдачи на руках/просроченные → «Отметить возврат» (Д-4) |

«Сервис временно недоступен, попробуйте позже», без повторов на запись.

**Новая ручка** (оба модуля, оба канала): `GET /appointments/me`,
`GET /library/me` → `{huid, roles}`. Из ЛК `roles` всегда пуст (Р-11).

## 7. Перенос данных

Разовые скрипты `scripts/` из MySQL ботов. В таблицах ботов есть **только HUID**
(username не сохранялся). С 2026-10-07 HUID — это и есть ключ пользователя (Р-8),
поэтому брони переносятся **напрямую по HUID**: сопоставлять с `employee_id` не
нужно, и брони сотрудников не из КЦ не теряются.

- каталог `Library_books` → `library_books` (без полей брони);
- будущие слоты `record_psy_pari` → `appointment_slots`, строки `DD.MM.YYYY` /
  `HH:MM` → `date` / `time`;
- будущие занятые слоты → `appointment_bookings` с `user_huid` из бота,
  `channel = express`, `user_name` — из ростера (если есть). Тип — из однозначного
  комментария или `--kind`. Строки только с `tg_id` (Telegram) не переносятся,
  попадают в отчёт;
- книги на руках → `library_loans` с `user_huid` бота (по фактам 2026-10-06 таких нет:
  все возвращены).

**Переключение (cutover).** Боты пишут в MySQL до последнего момента, поэтому
перенос делается в окно, когда оба бота остановлены: остановить боты → перенос
`--apply` → запустить новые версии ботов. Слоты и каталог, заведённые в сервисе
до окна, не дублируются (перенос идемпотентен). Прошлую историю не переносим: она
остаётся в MySQL (только чтение) до подтверждения переноса.

## 8. Тесты и выкатка

**Тесты:**

| Уровень | Что | Чем |
|---|---|---|
| Домен | Лимит 4/месяц (граница месяца, прошедшие считаются, отменённые — нет); 14:00 МСК (13:59 vs 14:00); отмена до/после начала; сроки и продление; просрочка | pytest, `now` явно |

| API | Роли (403), чужое (404), гонка за слот (409), **общий лимит: 2 брони из ЛК + 2 из бота → пятая отклоняется в любом канале**, уведомление только после коммита | `db` (testcontainers Postgres) + `FakeNotifier` |
